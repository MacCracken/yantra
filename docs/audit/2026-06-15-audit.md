# Security audit — 2026-06-15 (M8, toward v0.9.0)

> First-party security audit of yantra at 0.7.0, opening the **M8 — Security
> hardening** milestone. Scope: the library surface (`src/`), the transports it
> rides, and the data that crosses the wire. yantra is a **client** — it drives
> browsers/devices over CDP and WebDriver/Appium; it never runs a server.
>
> Method: source review against the M8 checklist (no-shell-out, control-byte
> sanitization, endpoint cert auth, info leakage), grounded in file:line, not
> assumed. Findings are tracked here with status; remediations land referencing
> this file.

| Area | Status |

## Scope of attack surface

yantra talks to three kinds of endpoint, all consumer-supplied:

- **Chromium DevTools** over a WebSocket (`src/protocol/cdp.cyr`, on `ws.cyr`).
  Commands are hand-built JSON; responses are parsed for the awaited id.
- **W3C WebDriver** drivers (chromedriver/geckodriver/WebKitWebDriver/
  safaridriver) over HTTP+JSON via sandhi (`src/protocol/webdriver.cyr`).
- **Appium** servers (UiAutomator2 / XCUITest) over the same sandhi WebDriver/
  Appium RPC (`src/mobile.cyr`).

Untrusted/attacker-influenced data that crosses these boundaries: selectors,
URLs, typed text, capability values (outbound); page-source, element text,
eval results, and **driver/server error bodies** (inbound). The audit follows
those flows.

## Findings

### F-1 — CDP JSON escaper drops control bytes (sanitization) — **FIXED**

`_cdp_b_esc` (`src/protocol/cdp.cyr`) escaped only `"`, `\`, `\n`, `\r`, `\t`.
Every other byte — including the C0 control range `0x00`–`0x1F` — was passed
through verbatim. Two problems:

1. **Invalid JSON.** JSON requires all U+0000–U+001F to be escaped; an unescaped
   control byte in a URL, selector, or `eval` string produced malformed CDP
   command JSON.
2. **ANSI / control-byte injection.** `0x1B` (ESC) passing through unescaped is
   exactly the terminal-escape-injection class M8 set out to close — a string
   round-tripped through yantra (e.g. echoed by a consumer that prints
   `yantra_eval_str` output, or a value built into a command) could carry an
   ANSI sequence.

**Remediation (this milestone):** the escaper now emits `\u00XX` for any byte
`< 0x20` not already covered by the named short escapes. Covered by a unit test
in `tests/m8.tcyr`. WebDriver/Appium paths were unaffected — they build JSON via
sandhi's `sandhi_json_add_string`, which already escapes the full control range.

### F-2 — No endpoint cert verification wired (transport) — **IN PROGRESS**

All current backends are localhost (drivers/Appium on `127.0.0.1`, plain HTTP),
so there is no live exposure today. But yantra sets **no TLS policy**, so the
moment a consumer points a session at a **remote** grid or cloud device farm
over HTTPS, the connection would rely on default trust with no pinning, mTLS, or
custom-CA option — and no way for the consumer to require verification.

The primitives to close this are present:

- **sandhi TLS policy** (`sandhi_tls_policy_new_pinned` (SPKI-hash pinning),
  `_mtls`, `_trust_store`, `_combine`) — the X.509 layer, settable per request
  via `sandhi_http_options_tls_policy`.
- **sigil** (`sigil_verifier_new`, `sigil_verify_hybrid`) — hybrid
  (Ed25519 + ML-DSA, post-quantum) signature verification, for authenticating a
  pinned endpoint-trust descriptor.

**Remediation (this milestone, per the "wire sigil now" decision):**

- **Done — sigil verification gate.** `src/security.cyr` adds
  `yantra_tls_pin_verify_ed25519(spki_hex, ed_sig, ed_pk)` and
  `yantra_tls_pin_verify_hybrid(…)` — they verify a sigil-signed SPKI cert-pin
  descriptor (Ed25519, or hybrid Ed25519 + ML-DSA-65) with `sigil_verify_hybrid`
  and, only on a good signature, return a `sandhi_tls_policy_new_pinned` handle;
  a bad/absent signature returns 0 + `YANTRA_ERR_VERIFY`. sigil is now in
  `[deps] stdlib` and the `[lib]` bundle. Covered by `tests/m8.tcyr` (sign →
  verify → tamper-rejects → null-guards), 14/14 offline.
- **Blocked — end-to-end application.** The pinned policy cannot yet be attached
  to the live driver traffic: sandhi's `sandhi_wd_*` / `sandhi_ap_*` RPC takes
  only a `base_url` (no options / TLS-policy parameter, no default), so only the
  session-create POST could be pinned, not the per-action calls. Filed as sandhi
  issue `2026-06-15-yantra-sandhi-wd-rpc-no-tls-policy`. Also needs remote-host support
  (host is hardcoded to `127.0.0.1`). Localhost sessions stay plain HTTP (no
  behavior change). F-2 closes when those land and the policy is threaded through
  the connect + per-action path.

## Verified-clean (no action)

- **No shell-out / process spawning.** No `execve`/`fork`/`system`/`popen`/
  process-spawn anywhere in `src/`. Browsers, drivers, and Appium servers are
  launched by the consumer / CI, never by yantra. The M8 "no shell-out for
  anything yantra does" rule holds by construction.
- **Error surface.** Every `_yantra_set_err` message is a static string literal
  except one (`src/mobile.cyr:182`), which is composed from integers
  (`stage`/`errkind`/`status`) plus a static sandhi error-kind name — no remote
  bytes, no secrets. `yantra_last_error_str()` returns these; nothing else is
  emitted. Internal state and session IDs do not leak into messages.
- **Opaque session IDs.** Session handles are integers into yantra's own
  registry; the driver-side session id is held internally and not surfaced in
  errors.
- **Outbound WebDriver/Appium encoding.** Selectors and capability values are
  placed into request JSON via sandhi's `sandhi_json_add_string` /
  `sandhi_json_obj_new` builders, which escape the control range. Raw-value
  insertions (`sandhi_json_add_raw`) are used only for yantra-controlled boolean
  literals (`"true"`), never for untrusted input.
